# 批量内容生产手册

多 agent 并发产出长文(白话、辩题导读、观书)的实战手册。
**这里只写踩过坑才知道的事**——理所当然的不写。每条都注明是怎么发现的。

---

## 一、并发编排

### 1.1 流式跑法 > 一次拉满

一次派 20 个 agent 齐发,**必撞会话额度上限**(实测两次全灭)。
改成「**同时最多 4–5 个、完一个补一个**」后,同样的量一次没撞。

系统上限是 20 个并行 subagent(超了报 `Concurrent subagent limit reached`),
但那是硬上限、不是安全线。

### 1.2 分片文件是并发的地基

**一篇一个独立文件**,写到 `scratchpad/<domain>-parts/<键>.json`,
**绝不写共享库**。主会话合并前逐片校验。

这套方案在本轮**兜住了五次中断**:
额度上限 ×3、进程退出 ×1、scratchpad 被清 ×1。每次都是「已写完的一篇不丢」。

配套的两条纪律缺一不可:

- **一篇写完立刻落盘**,不许攒到最后。攒着的那批在 scratchpad 被清时全丢了。
- **攒一批就入库一批**,主会话别等最后统一合并。
  scratchpad 被清那次,已入库的 86 篇一篇没少;若等最后合并会全没。

### 1.3 禁止 agent 转包子 agent

踩过:某 agent 把整批活分给子 agent 后**自己提前返回**,回报「等它们完成」。
子 agent 的产出没落到约定目录,父 agent 却已交差。

**更麻烦的是误判**:我当时查分片目录为空,下结论「一篇未写」——**判早了**。
子 agent 其实还在跑,两分钟后陆续落盘。等发现时已重派了一个,好在及时杀掉。

两条教训:
- prompt 里明写 **`不许转包子 agent`**
- **不能只查一次目录就下结论**;父 agent 报完成 ≠ 文件已就位,也 ≠ 文件永不就位

### 1.4 agent「失败」不等于没产出

大量 agent 报 `session limit` / `Connection closed` 而终止,但**文件其实已经写完落盘**。
每次都要先查分片目录再决定是否重跑——本轮至少三次「报失败但全部完成」。

## 二、主会话的合并校验

**不采信 agent 自查**,入库前主会话逐片重验。这道关逮到过:

| 逮到的问题 | 怎么发现的 |
|---|---|
| quote 白话字段写成 `text`(渲染器只认 `translation`) | agent 主动报告,查渲染器坐实;顺带扫出存量数据 1 处同样的老 bug |
| `steps` 块的项字段写成 `steps`(应为 `items`) | check-data 报错;`assemble-baihua.mjs` 本有此归一,自建合并脚本漏了 |
| 篇幅超上限 | **我的校验一开始只查图数/pull/引文/颜色/引号,漏了字数**,放进去 4 篇超限初稿 |
| 篇幅低于下限 | 补上下限后逮到 2 篇(源文太短的篇目) |

**字数口径**:剥掉 SVG 内文字后数汉字。
```python
n = len(re.findall(r'[一-鿿]', re.sub(r'"svg":"[^"]*"', '', json.dumps(a, ensure_ascii=False))))
```

**弯引号检查要分书**:多数书禁弯引号,但《长短经》卷十底本正文自带 193 处弯引号
(卷八用「」)。故检查改为**只在 `quote.original` 之外查**——原文照录,自撰文字用「」。

## 三、内容质量

### 3.1 引文一律脚本切片,严禁手打

主会话写 briefing 时**凭记忆写的细节被 agent 纠正过十余次**:
褒裳主语、伐檀作「寘」、东山作「蒙」、鸿鴈作「嗸嗸」、常棣「不如友生」在第五章、
大东作「澘」「睆」、墨子「穷人所术」、《说难》「遂物」而非「逐物」……

**结论:主会话的看点提示只作定位,一切以切片脚本输出为准**,并在 prompt 里明说这条。

### 3.2 归给「站内注疏」的训释必须真的核过

每一波抽查都逮到过冒领。prompt 固定要求:
**注疏没收的一律明写「注疏未收、为注家通说」**。

### 3.3 跨篇结论要 grep 坐实,不靠背书

本轮靠 grep 得出的、经复核属实的结论举例:

- 「仁」在三百篇**仅两见**,且两次都夸猎人(两个 agent 独立得出,互相印证)
- 「周公」全书仅见《破斧》与《鲁颂·閟宫》——故《豳风》其余六篇的周公之说全是旧说
- 「携手」仅见《北风》一诗、一连三次
- 「于嗟」全书 11 见分 5 篇
- 「是以为刺」是全书**唯一自报作诗动机**的句子

**反例**:主会话凭印象说「某某名句在某篇」,grep 后发现根本不在——所以这条是硬规矩。

### 3.4 校验脚本查不出事实错误

check-data 查得出结构和引文子串,**查不出「三百零五首排在它后面」实应 304 这类错**。
那是人读抽查逮到的。**每波必须人读一篇**。

### 3.5 同名篇目按键派活,不按名字

《诗经》有柏舟/谷风/扬之水/羔裘/甫田/杕杜/无衣/黄鸟/白华各两三首。
prompt 里必须显式警告 + 要求「写前先打印切片核对」+ 要求在回报里注明取的是哪一首。

引同名的另一首时:**只入正文、不进 quote 块**——引文校验池收窄到本篇,放进去必判错。

### 3.6 跨篇口径要对齐,但要做出差异

同一结论被多篇触及时(如「彼其之子是套语」「羔裘只标身份不带褒贬」),
prompt 里点明已有篇目、要求**口径一致但措辞另写**。

做得好的例子:`8-6` 南山发现前篇说「绥绥仅两见」而 grep 实为 4 次出现(1 处 + 三章重唱),
遂改写为「**只出现在两首诗里**」——结论一致而数字准确,两篇都不算错。

### 3.7 回报要极简

单篇详细回报很有价值,但 80+ 篇的量级会吃光上下文。
**大批量时要求「每篇一行」**,详细核查由主会话自己做。

## 四、红线的守法

「不作 X」写在 prompt 里不够,**要给 agent 可操作的替代动作**。本轮验证有效的几种:

- **给理由驳回**而非回避:`出其东门` 驳「专一」鸡汤读法时给三条理由(诗中对「如云」者
  无一字褒贬、「缟衣綦巾」是平民装束的写实、若照毛序则语境是乱世流离)
- **从内部堵死**:`bushi` 卜筮的收束用三家共有的「不许人撒手等命」——比外部声明有力
- **划到具体位置**:`tonglei` 涉《系辞》,明确「把大衍揲蓍整段一概不涉、只取末句论推类」,
  不是笼统说「不讲占法」
- **主动避引**:`kongyou` 为守佛组红线,自觉避开「能除一切苦」这类经末愿文
- **老实说不适用**:`yong` 指出太公根本不在那条轴上,不硬凑五家对辩

## 五、这套流程适合什么、不适合什么

**适合**:体量大、单元独立、有可机器校验的正确性约束(引文必须是原文子串)的内容。

**不适合**:需要通盘一致性的内容(如全书导论),以及事实密度高而无法自动校验的内容
——后者做出来也得人读一遍,省不下多少。
