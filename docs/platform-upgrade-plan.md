> 状态:**规划已定案(§4 决策记录,2026-07-13),按 Phase 0→1→2→3 分期动工,进度按 §6 TODO 清单逐项打勾跟踪**。

## 0. 总纲:为什么做,按什么原则做

### 0.1 目标

观象已完成从「一个易经站」到「十组典籍 + 白话 + 观书」的内容长征,当前形态是**纯静态个人站**:React 19 + Vite、无后端、用户数据只存 localStorage(封装在 `src/features/yijing/storage.js`,键前缀 `guanxiang.v1.`)、Cloudflare Pages 托管(`hexa.gavin.pub`,owner 用 CF 后台拖 `dist/` 部署)、iOS App(Capacitor,TestFlight 内测)。

这次升级要把它推进一步:**从「只读的静态站」升级为「可互动、可沉淀用户、承载个人品牌」的产品**——读者能登录、收藏批注能跨设备带走、能留言评论、owner 能看到谁在读什么;同时把「谁做的、为什么做」用与全站朱印视觉一致的方式钤在页面上。

### 0.2 设计原则(贯穿全文)

1. **优先复用 Cloudflare 生态**。托管已在 CF Pages,新增的后端函数、数据库、防刷、访问统计一律优先选 CF 自家件(Workers / D1 / KV / Turnstile / Web Analytics)——不新增供应商关系、免费额度充足、一个后台管完,契合 owner「谨慎对待第三方依赖与运营成本」的一贯偏好。
2. **克制,不过度设计**。继续「自己动手做细节」的风格:落款组件、统计仪表、分享卡主题都是自写小组件(全站至今不引入 UI 组件库,本次也不破例);后端只写必要的几个接口,不上框架、不上 ORM、不上重型 BaaS 套件。
3. **隔离「高摩擦、依赖现实世界审批」的事项**。个人备案审批周期以周计、且牵动 owner 之前放弃阿里云的历史教训(§2.6 详述)——把它单独隔成 Phase 3。**owner 已拍板**:不注册企业/个体工商户,微信登录彻底放弃,只办个人备案;个人备案可与 Phase 0–2 并行提交办理,**不构成阻塞关系**,只是不指望它在 Phase 0–2 的时间线内批下来。
4. **尊重既有部署习惯**。owner 已明确否决 wrangler CLI 自动部署,坚持 CF 后台手动操作——本规划的后端部分同样按「CF 后台可完成」设计(Workers 支持后台在线编辑与粘贴部署,D1 可在后台建表跑 SQL);若日后接口多到后台维护吃力,再由 owner 决定是否松口给 CLI,规划不预设。
5. **隐私底线不退**。埋点不采集可识别个人的信息;评论防刷用隐私友好的 Turnstile 而非 reCAPTCHA;二维码、图表等一律本地生成不发外部请求(延续现有 CSP 严格与「纯前端自足」的做法)。

## 1. 技术架构总方案

### 1.1 后端:Cloudflare Workers + D1(推荐)

**推荐:一个 Cloudflare Worker(挂 `hexa.gavin.pub/api/*` 路由)+ 一个 D1 数据库,不引入 KV。**

理由:与 Pages 同账号同后台,零新增供应商;D1 是 SQLite 兼容的边缘数据库,免费额度(读 500 万行/日、写 10 万行/日、5GB 存储)对个人站的登录/收藏/评论/埋点绰绰有余;Worker 免费档 10 万请求/日同样够用。前端只需把 `fetch('/api/...')` 当普通接口调,静态站的架构与部署流程完全不动——**没有后端时全站照常可用**(接口全部设计成增强型:登录/同步/评论不可达时,localStorage 行为原样保留)。**不引入 KV**:KV 免费档写/删/列操作仅 1000 次/日,比 D1 紧一个数量级,原计划里"高频计数存 KV"这条已确认没必要——`/admin/stats` 的聚合(七日曲线、Top N 等)直接对 D1 跑实时 `GROUP BY` 聚合查询即可,当前预估的日请求量级(§2.3)下 D1 完全扛得住,不需要多一层缓存,少一个组件、少一处出错点。

主要备选与取舍:Supabase(Postgres + 现成 Auth,功能更全但引入新供应商、免费档有休眠限制,且其现成 Auth UI 与观象视觉不合,还是得自己写壳)——在「owner 想省掉自写登录逻辑」时才值得考虑;本规划按 Workers + D1 走。

**为迁移预留退路(建议现在就做)**:Worker 代码建议用 **Hono** 写(而非裸写 Workers `fetch` handler)——它的路由/中间件写法接近 Express,但同一份代码可无缝跑在 Cloudflare Workers / Node.js / Deno / Bun 上,只需换启动适配层。这样若日后决定迁移到自建服务器(如 ECS),业务逻辑代码基本不用重写,只需替换「怎么拿数据库连接、怎么启动进程」这一薄层——把原本一次昂贵的应用重写,压缩成换一层壳。**数据库层的迁移成本**:D1 是 SQLite 方言,`wrangler d1 export` 能导出标准 SQL,但不能直接导入 Postgres/MySQL(类型与语法不兼容);本规划的表结构简单(6 张小表),写一次性转换脚本约一天工作量,若目标库仍用 SQLite 则近乎文件级搬运。**D1 备份**:自带 Time Travel,免费档可回溯 7 天、Paid 档 30 天,默认开启不用配置;超过 30 天的长期归档需自建定时任务(Workflows/Cron)导出到 R2。Turnstile 不绑定 Cloudflare 托管,搬到别处一样能用,不算迁移成本。

### 1.2 登录:海外 Google + 邮箱验证码;国内手机验证码;微信缓议

- **Google**:用 Google Identity Services(GIS)标准 OAuth,免费、文档成熟。前端渲染 GIS 按钮拿 ID token → POST 给 `/api/auth/google` → Worker 验签、按 `sub` 建/查用户、发会话。
- **邮箱**:**推荐做「邮箱验证码/魔法链接」而非传统密码**——省掉密码哈希存储、强度校验、忘记密码整条负担。需要一个发信服务,推荐 Resend(免费 100 封/日、3000 封/月,API 一个 POST 即发,Worker 里直接调)。
- **国内(手机号+短信验证码)**:作为微信登录的**推荐替代**(依赖链见 §2.6),阿里云短信或腾讯云短信皆可(按条计费约 ¥0.045/条,月成本以个位数元计),Worker 调其 API 发 6 位验证码。注意:短信签名需要一次性的实名/网站材料审核(个人可办),但**不需要企业资质、不需要备案**。
- **微信**:**已定案不做**(§2.6),`identities.provider` 预留 `wechat` 字段仅作扩展位,无实施计划。

会话统一用 Worker 签发的 JWT(HttpOnly cookie 为主;Capacitor 壳内 cookie 跨源不稳,iOS 端改存 token 于 Capacitor Preferences,请求带 `Authorization` 头——`/api/auth/*` 两种都收)。

### 1.3 防刷:Cloudflare Turnstile

评论提交、验证码发送这两个写接口前置 Turnstile(免费、无感验证、隐私友好、同生态,不依赖 Google reCAPTCHA)。前端一个 widget,Worker 端一次 siteverify 校验,半天工作量。

### 1.4 数据表草案(字段级设计意图,DDL 落地时再细化)

| 表 | 字段(意图) | 说明 |
|---|---|---|
| `users` | id(uuid)、display_name、avatar_seed(生成式头像种子,不存上传图)、created_at、is_owner(布尔,owner 账号标记,统计后台/评论管理鉴权用) | 一人一行,与登录方式解耦 |
| `identities` | user_id、provider(google/email/phone/wechat 预留)、provider_uid(Google sub / 邮箱 / 手机号哈希)、created_at | 一人可绑多种登录方式;手机号哈希存储不存明文 |
| `auth_codes` | target(邮箱/手机号)、code_hash、expires_at、attempts | 验证码短时效表,过期即清 |
| `user_data` | user_id、key(reading/corpusMarks/corpusNotes/settings…)、value(JSON)、updated_at | **云同步表:直接映射现有 localStorage 的 DATA_KEYS 白名单**,粗粒度整键存取,先不做逐条合并 |
| `reading_events` | client_id(localStorage 匿名随机 id)、path、corpus、slug、chapter、dwell_ms(粗粒度停留)、ts | 匿名埋点,无 IP、无 UA 指纹、与 users 不关联 |
| `comments` | id、user_id、corpus、slug、chapter(挂载锚)、body(纯文本,长度上限)、status(visible/hidden)、created_at | 扁平评论,owner 可改 status |

## 2. 逐项功能设计

### 2.1 License:CC BY-NC 4.0

**做法**:仓库根目录加 `LICENSE` 文件(CC BY-NC 4.0 国际版全文或官方 deed 链接 + 授权声明段)。

**必须写清授权范围**——这是本项最重要的一句话:

- **覆盖**:owner 的**原创内容**——白话文章(`src/data/*/baihua/`)、逐段注疏与译文(`scripts/authored/`、`zhushi-anchored/`)、每章延伸、思想脑图、观书的封面/脑图/文章、原创 SVG 配图、辩论内容(debates)等。
- **不覆盖**:公版古籍原文本身(hexagrams.json、classics/*.json 等管线抓取物)——那些是公共领域,**不属于任何人可授权的范围**,声明里要明说,避免「把《论语》据为己有」的观感与法律瑕疵。

**代码是否一并覆盖:已定案——CC BY-NC 4.0 统一覆盖内容与代码,不拆双协议、不另加 `LICENSE-CODE`。** 附注一句:CC 系列本不为软件设计(无专利条款,"衍生作品"对编译型代码的语义比较模糊,FSF/OSI 均不建议给代码用 CC),但观象是个人站、不是被他人拿去二次分发的库,统一用它不影响实际使用,不必为此另起一套代码许可证。

落地物:仓库根目录一份 `LICENSE`、README 与落款组件(§2.2)里各引一段一致的范围声明。

### 2.2 落款/版权标记:「钤印」组件

**设计:与全站朱印视觉呼应的「钤印 → 跋」结构。**

- **入口**:全站页脚(及总门户底部)一枚小朱印图标——建议刻「**跋**」字(篆意,与左上角「观」印首尾呼应:观为起、跋为收),半透明弱化存在感,hover 显「落款」提示。
- **点开**:一个浮层(复用 `SettingsSheet.jsx` 的浮层模式与样式基座,新组件 `src/features/Colophon.jsx`),同时给一个独立路由 `/ba`(可分享、可被搜索引擎收录)。浮层与整页共用一份内容组件(仿 `BaihuaBlock`/`BaihuaArticle` 的「抽屉与整页共用」拆法)。
- **内容区块**(数据集中在 `src/data/colophon.json`,改文案不动组件):
  1. **署名**:创作者 ID(gaojiasheng)+ 一句身份定位;
  2. **缘起**:一段「为什么做观象」的话——这是个人品牌的核心位,建议 owner 亲笔;
  3. **联系方式/外链位**:邮箱、GitHub、社交账号(留插槽,owner 填);
  4. **协议声明**:引 §2.1 的范围声明(原创内容 CC BY-NC 4.0、古籍原文公版、代码另议),链到 `/LICENSE`;
  5. **版本与更新**:构建时注入 `__APP_VERSION__` + 构建日期(vite `define`,零运行时成本);
  6. **鸣谢**:AI 辅助制作说明(译注/白话由 AI 辅助生成、owner 审校把关——如实署明,既是诚信也是特色)。
- **挂载**:做成**全站共享组件**挂在 App 外壳层(与 nav/SettingsSheet 同层),十组分站 + 中立外壳(门户/concepts/debates/books)一次全覆盖,**不在各分组重复实现**;印章颜色随 `data-site` 取组 accent,中立外壳用默认朱红。

零后端、纯前端,Phase 0 即可上线。

### 2.3 阅读统计(后台可见)

分两层,先易后难:

**⑴ 全站基础访问量:Cloudflare Web Analytics**。免费、无 Cookie、CF 后台一键开启(Pages 项目设置里勾选即可自动注入,或手贴一行 beacon 脚本进 `index.html`)。当天就能回答「有没有人来、来了多少、看了哪些路径」。**这一项零开发量,建议立刻开。**

**⑵ 精细阅读埋点(哪本书/哪一卦/哪一章读得多、停留多久):自建轻量打点。**

- 前端:新增 `src/features/telemetry.js`——路由切换与 `visibilitychange`/`pagehide` 时用 `navigator.sendBeacon('/api/beat', …)` 上报 `{cid, path, corpus, slug, chapter, dwell_ms}`;`cid` 是首访生成、存 localStorage 的匿名随机 id(键 `guanxiang.v1.cid`,**不入 DATA_KEYS 导出白名单**)。不采集 IP、UA 指纹、任何可识别个人的信息;dwell 只取粗粒度(如 10 秒桶)。**"离开上一页"与"进入新页"合并成一次 beacon**(而非各打一次),减少一半请求量。
- 后端:Worker `/api/beat` 做基本校验(路径合法、限频)后**直接写 D1 `reading_events`**(D1 免费写配额 10 万行/日,足够单独扛住埋点)。**不引入 KV 做中转**(见 §1.1)——写入直落 D1。
- **后台页 `/admin/stats`**:仅 owner 可见,鉴权**做成自动收口、不依赖人为记得手动切换**——过渡期(Phase 1,登录体系还没上线时)用环境变量口令(Worker secret)兜底;但 `/api/admin/*` 的校验逻辑写成「**只要 `users` 表里已存在 `is_owner=true` 的正式账号,口令验证直接失效,强制走登录**」。也就是说:Phase 2 登录一上线、owner 自己用正式账号登录过一次,临时口令自动作废,不需要日后手动回来删代码或改配置——避免"过渡方案"变成"永久遗留"。图表数据**直接对 D1 跑实时 `GROUP BY` 聚合查询**(不预计算缓存),复用项目里已有的数据可视化语言(自绘 SVG 条形/折线,朱色 accent、衬线标注,参照白话配图与辩论图谱的做法,不引图表库):七日曲线、分组热度榜、书/章 Top N、平均停留。

**容量估算(按 owner 目标场景计算,已定案)**:全站行为分三类——⑴翻章埋点(`reading_events` 写,量最大);⑵登录/同步(`users`/`identities`/`user_data` 写,已登录用户日常阅读不重复触发);⑶评论(`comments` 读写,**评论列表必须懒加载**——打开章节页不自动拉取,用户主动点开才发请求,否则量级会追平埋点、直接把总请求数翻倍)。**目标场景:日活 2000、人均单次登录看 10 篇文章**——按 10 次翻章埋点 + 已登录用户摊薄后 <1 次会话 + 1–2 次收藏批注同步(防抖)+ <1 次评论(懒加载),每活跃用户/日约 **13–15 次请求**。2000 × 15 ≈ **3 万次/日**,仅占 Workers 免费 10 万请求/日额度的 **~30%**、D1 免费写 10 万行/日额度的 **~24%**——**目标场景在免费档内有 3–4 倍安全余量,现在不需要为 Workers Paid 做预算**,免费档实际能撑到 6000–7000 活跃 DAU 才会顶到天花板。

### 2.4 登录功能

按 §1.2 架构落地,四小节:

1. **Google**(Phase 2):GIS 按钮 → `/api/auth/google` 验 ID token → 建/查 `users`+`identities` → 发会话。登录 UI 做进一个新的 `src/features/auth/AuthSheet.jsx` 浮层(视觉沿用 SettingsSheet 基座),入口放 nav 与「我的」页。
2. **邮箱验证码**(Phase 2):输邮箱 → `/api/auth/email/send`(Turnstile + Resend 发 6 位码)→ `/api/auth/email/verify` 换会话。不做密码。
3. **手机号验证码**(Phase 2 末或 Phase 3 初,国内替代方案):流程同邮箱,发送通道换阿里云/腾讯云短信。它就是「国内用户友好登录」的答案本体,**不依赖备案与企业资质**(详 §2.6)。
4. **微信**:**已定案不做**(§2.6)。`identities.provider` 已预留 `wechat` 字段位,仅为将来万一改主意留一个不用改表结构的口子,当前无实施计划。

**登录的「顺带」价值——云同步,这才是对读者的真卖点**:登录后把现有 localStorage 的收藏/批注/阅读进度/设置(即 `storage.js` 的 DATA_KEYS 白名单,导出导入功能已验证过这套数据的可序列化性)同步到 D1 `user_data` 表——「换设备、换浏览器、web 和 iOS App 之间,足迹都能带走」。同步策略从简:登录时拉云端与本地按 `updated_at` 取新,之后写操作防抖推送整键;冲突不做逐条合并(个人学习数据冲突概率低,先粗后细)。**未登录用户一切照旧**,登录永远是可选增强。

**已定案:Phase 2 先做 web-only 登录,iOS 端后补。** 因为 iOS App 是 Capacitor 直接封装同一份 web 代码(同源同构建),若不特殊处理,登录上线当天 iOS 壳里也会"看得到"登录入口——但 iOS 端的会话存储(Capacitor Preferences)、cookie 跨源行为都还没适配,点了会不工作。落地方式:登录入口加一个 `Capacitor.isNativePlatform()` 平台判断,**iOS 壳内这一阶段直接隐藏登录入口**(或显示「即将支持」的禁用态),避免看得到用不了的体验;等 iOS 端登录适配完再放开。这也顺带简化了 Apple 登录合规问题——**iOS 端这阶段完全不提供第三方登录,不触发 App Store 审核指南 4.8 条款(该条款仅在 App 内提供第三方登录时才要求同时提供 Sign in with Apple)**,只有日后 iOS 也接入 Google 登录时才需要补 Apple 登录。

**内容侧不受影响**:登录是新增的独立功能层,不碰现有内容生产管线(数据文件/`check-data`/build 流程)——iOS App 该发的内容版本(白话/观书等)照常按原节奏发,不会因为做登录被拖慢,两条线互不占用。

### 2.5 数据库 + 评论系统

数据库即 §1.1 的 D1,表见 §1.4。评论系统设计要点:

- **挂载粒度:每章/每篇文章一个评论区,先不做逐段评论。** 理由:全站内容单元数量巨大(仅白话就 834 章,段落以万计),过细粒度必然导致大面积空评论区——对冷启动是灾难(读者看到的永远是「暂无评论」),对 owner 是管理噪音。每章一区,评论密度才可能聚起来;逐段评论留作日后数据证明有需求时的升级项(锚字段 `corpus/slug/chapter` 已够用,加 `para` 即可扩展,不用改架构)。
- **形态:扁平评论,不做多层嵌套回复。** 个人站体量下嵌套树是过度设计;先做「发布 / 时间倒序列表 / owner 置顶一条」的最小集。
- **防刷**:提交前 Turnstile 校验 + 登录后才能评论(匿名评论不开,省一整套治理成本)+ Worker 端限频(同一用户每分钟 N 条)。
- **管理**:owner 登录后(`is_owner`)在评论区内直接见「隐藏/删除」按钮,另在 `/admin/stats` 加一个最近评论流页签,无需独立管理后台。
- **前端**:新组件 `src/features/comments/CommentSection.jsx`,挂在 `ClassicReader` 章末区(顺位排在 原文→注疏→延伸→白话 之后,即最末),白话整页(`BaihuaPage`)与观书文章页视情况复用。接口:`GET /api/comments?corpus=&slug=&ch=`、`POST /api/comments`、`PATCH /api/comments/:id`(owner)。

### 2.6 域名备案:已定案——个人备案,不接微信

先把核实过的事实链摆平(以下为已核实结论,直接采信):

1. **ICP 备案只在网站使用中国大陆境内服务器或大陆 CDN 节点时才强制**。观象当前纯 Cloudflare Pages 境外托管(未启用大陆节点),**不需要备案,现状完全合法合规**。
2. **微信开放平台「网站应用」的微信登录,个人开发者无法申请**——资质认证要求组织主体(企业或个体工商户),认证费 ¥300。这条路对纯个人身份**彻底走不通,没有绕开的办法**。
3. **ICP 备案本身不要求企业资质**——工信部备案系统区分「个人」与「单位」两类主体,个人拿身份证就能办「个人备案」。

**owner 已拍板:办个人备案,但不注册个体工商户/企业,因此微信登录彻底放弃(§1.2 的手机号验证码是国内登录的终态,不再是"备选",是唯一方案)。** 这比原来摆出的「路线 A(备案+微信+企业资质全套)/路线 B(什么都不做)」更轻——是一条介于两者之间的选择:只解决"域名合规接入大陆节点"这一件事,不背微信那条企业资质链。

**要注意的一点(备案≠零成本,即使是个人备案)**:个人备案实操上通常仍要选一个「接入商」办理——大多数情况下要在某个大陆云厂商(阿里云/腾讯云/华为云)那开一个账号、哪怕只挂一个最低配资源作「备案载体」,这是行政流程要求,不是纯粹的技术选型。也就是说,**即使不做企业资质、不接微信、不搬迁整个后端,备案这个动作本身大概率还是要重新开一个大陆云账号**——这正贴着 owner 2026-06 因「域名转发/备案受限」放弃阿里云的教训。建议动手前想清楚:当时具体卡在「转发」这个操作方式,还是「备案审批」本身?如果是前者,这次直接走完整备案流程(而非转发)大概率顺利很多。

**备案下来之后怎么用这个域名(默认方案)**:不建议把整个后端搬去大陆——**默认做法是给静态资源接一层大陆 CDN、回源到现有 Cloudflare Pages**(源站不动,只加速大陆分发);API 仍留在 Workers/D1,不受影响。这样改动面最小,备案只解决"访问速度"这一件事,不触碰已经谈好的 Workers+D1 架构。具体接哪家 CDN、怎么配回源,等备案真的批下来再细化,**不阻塞 Phase 0–2 现在动工**。

### 2.7 分享卡多主题 + 二维码

基于现有 `src/features/reader/QuoteCard.jsx`(SVG 现卡 → canvas → PNG 下载,`fonts.ready` 保衬线,已挂全站读经页 🖼 入口)扩展,**不重写,做主题化改造**:

- **主题预设**:把当前写死的底色/边框/印色抽成 `THEMES` 常量表(每套约 8 个 token:底、边、原文色、译文色、印底、印文、饰纹、署名色),先做 4 套:
  1. **朱印经典**(现款保留,默认);
  2. **水墨留白**:纯白底、淡墨细边、原文墨黑、印章为唯一朱色点睛;
  3. **暗夜月白**:深墨底、月白文字、印章暗金——适合深色系社交环境;
  4. **节气应景**(可选,做完前三套再议):按当日节气取一组低饱和配色 + 角落节气名小字,数据一张 24 节气表,纯本地计算。
- **切换 UI**:`quote-modal` 里卡片上方一行主题圆点(swatch,点击即切,选中态描 accent 环),记住上次选择(localStorage 键 `guanxiang.v1.quoteTheme`,入 DEFAULT_SETTINGS 白名单)。
- **二维码**:
  - **生成**:纯前端本地生成,推荐 `qrcode`(node-qrcode,零依赖、支持输出 path 数据),**不发任何外部网络请求**(契合现有 CSP 严格做法)。这是本次规划唯一新增的前端 npm 依赖,体积 ~15KB gzip,可接受;若 owner 连这个也不想加,备选是把 QR 矩阵算法内联自写(工作量约两天,不推荐)。
  - **内容**:当前段落/卦/文章的**精确深链接**(读经章 `https://hexa.gavin.pub/<corpus>/<slug>/<ch>#p<段>`、卦页 `/hexagram/<id>`、白话整页 `/…/baihua/<ch>`——路由现成,无需新增)。
  - **视觉融合**(关键,不能是黑白码块糊上去):QR 以 SVG path 画进卡片**右下角署名区旁**,尺寸约 88px;前景色用当前主题的印色/墨色(非纯黑),背景透明直接落在卡底上;码的中心定位区外留白处**叠一枚微缩「观」印**(QR 容错率设 M/Q,中心遮挡 ~8% 内可正常扫描);外圈用主题色描一圈 1px 细边框,让它读起来像卡片版式里的一方「印」,而不是外来贴片。扫码率注意:前景/背景对比度保持 4:1 以上,暗夜主题下 QR 用月白前景。
- **顺带**:卡片署名行下加一行小字「扫码读原文 · 观象」,把二维码的用途说破,提升实际扫码转化。

零后端,Phase 0 可做。另:`index.html` 已有站点级静态 OG meta,逐页动态 OG 依旧受限于纯静态托管,**接了 Worker 之后**可加一个 `/api/og` 兜底(对爬虫 UA 返回带书名章题的 HTML meta),列为 Phase 2 的可选加分项,不占主线。

## 4. 决策记录(已拍板,2026-07-13)

以下 6 项在规划初稿时是开放决策,owner 已逐条表态,不再是待办:

1. **License 是否覆盖代码**——**已定案:CC BY-NC 4.0 统一覆盖代码与内容**,不拆双协议、不另加 `LICENSE-CODE`。(§2.1)
2. **评论挂载粒度**——**已认可**「每章/每篇一区、扁平不嵌套、登录才能评」的最小集,按此设计推进。(§2.5)
3. **备案+微信**——**已定案:个人备案(不注册企业/个体工商户),微信登录彻底放弃**,国内登录以手机验证码为终态方案。(§2.6)
4. **统计后台鉴权**——**已认可**过渡期口令方案,但**要求自动收口、不依赖人为记得手动切换**:`users` 表出现正式 `is_owner=true` 账号后,口令验证自动失效、强制走登录,已写入 §2.3 的实现约束,不再是待权衡项。
5. **新增依赖底线**——**已认可**`qrcode`/Resend/Turnstile/短信服务这几项新增依赖,均在可接受范围内。
6. **iOS 上架与登录的合规联动**——**已定案:先 web-only 登录,iOS 端后补**;通过 `Capacitor.isNativePlatform()` 判断在 iOS 壳内隐藏登录入口,避免看得到用不了,也避免过早触发 Sign in with Apple 的合规要求;内容生产节奏(白话/观书/TestFlight 发版)不受此影响,两条线互不占用。(§2.4)

技术风险备注(非决策项,仅记录):D1/Workers 免费额度对当前体量(§2.3 已按 2000 DAU 测算)有 3–4 倍余量;埋点是全站最高频写入,`/api/beat` 需带限频、直落 D1(不经 KV);云同步采用整键覆盖策略,极端多端并发下可能丢最后一次编辑之前的中间态——个人学习场景可接受,先粗后细。
